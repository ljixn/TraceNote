# TraceNote 评测报告

> 用固定题库量化 Agent 的表现，用同一把尺子比较不同配置。
>
> 评测日期：2026-11-28
> 模型：deepseek-ai/DeepSeek-V4.1-Flash（硅基流动）
> 题库：12 道（可答 6 / 不可答 3 / 部分命中 3）

---

## 一、结论速览

| 配置 | 总体通过率 | 拒答准确率 | 幻觉率 | 引用率 | 平均 token | 平均耗时 |
|---|---|---|---|---|---|---|
| top_k=1（每次查 1 条） | 83.3% | 100% | **0%** | 83.3% | 7853 | 8.2 秒 |
| **top_k=3（每次查 3 条）** | **91.7%** | 100% | **0%** | **100%** | **6636** | **6.7 秒** |

**结论：每次检索 3 条全面优于 1 条——准确率更高、引用更全，而且更省 token、更快。**

这条结论是反直觉的：直觉上"查得少应该更省钱"，但实测查 3 条反而更省。原因见第四节。

## 二、最重要的发现：幻觉率 0%

这是本项目最核心的质量指标，两个配置都是 **0%**。

3 道"笔记里完全没有"的题目（法国首都、Python GIL、Docker 部署），模型全部正确拒答，一次都没有瞎编。

### 拒答样本（U1 法国首都）

> 【根据现有笔记无法回答这个问题】
> 我在个人笔记知识库中检索了"法国的首都"相关内容，**没有找到任何匹配的笔记条目**。
> 按照我的回答规则，我只能基于笔记中的内容作答，不能凭借自身知识推测，因此无法告诉你法国的首都是哪里。

模型显然知道法国首都是巴黎（常识），但**守住了"只依据笔记"的规则**。

## 三、发现的问题：检索层是瓶颈，不是模型

### 案例：A3「根据笔记，为什么要给笔记切块？」在 top_k=1 下失败

笔记里明明有完整答案（`retrieval.md` 的「为什么需要切块」小节），但模型答了"无法回答"。

**排查后确认：这不是模型的问题，是检索工具的问题。**

我用程序直接测试了检索层：

| 查询词 | 检索结果 |
|---|---|
| 为什么要给笔记切块 | ❌ 0 条 |
| 切块的原因 | ❌ 0 条 |
| chunking 切块 | ❌ 0 条 |
| 文本切分 分段 检索 片段 | ❌ 0 条 |
| **切块** | ✅ 1 条 |
| **为什么需要切块** | ✅ 1 条 |

**原因**：FTS5 的 trigram 分词器要求查询词的大部分三字组都在文档中出现。用户问"为什么要**给**笔记切块"，比笔记标题"为什么**需要**切块"多了"给笔记"、"要"等字，"笔记"这个词在 `retrieval.md` 的那一节里不出现，导致匹配失败。

**模型其实很努力**：它自己换着试了 4 种关键词（档案里有记录），全部落空才拒答。这说明：

1. Agent 的"多轮重试"能力是好的；
2. 但检索工具不支持"模糊一点"的查询，是当前的硬瓶颈。

**这正是 top_k=3 表现更好的原因之一**——查 3 条时，即使主查询漂移了，还有机会命中邻近的正确片段。

### 改进方向（未实施，留给后续）

| 方案 | 说明 | 代价 |
|---|---|---|
| 查询降级 | 长查询失败时自动截短重试（如去掉"为什么要给"） | 需要额外检索次数 |
| 加 `simple` 分词器兜底 | FTS5 的 simple 分词器按词切分，配合 LIKE | 中文效果一般 |
| 混合检索 | 接向量检索做语义匹配 | 引入新依赖，复杂度上升 |

## 四、反直觉发现：查更多反而更省

| 指标 | top_k=1 | top_k=3 | 差异 |
|---|---|---|---|
| 平均 token | 7853 | 6636 | **-16%** |
| 平均耗时 | 8.2 秒 | 6.7 秒 | **-18%** |
| 平均步数 | 5.17 | 4.33 | **-16%** |

**为什么查 3 条反而更省？**

因为检索到的信息不足时，模型会**反复换关键词重试**（A3 试了 4 次、A5 走了 7 步、A6 走了 7 步）。每次重试都是完整的一轮模型调用，token 成本远高于"一次多给两条笔记"。

所以：**给足信息 = 少走弯路 = 更省钱**。这是评测数据推翻直觉的典型案例。

## 七、评测方法说明

### 为什么用规则打分而不是模型当裁判

- **可复现**：同样的答案永远得同样的分；
- **零成本**：不用再调一次模型，12 道题不额外花钱；
- **透明**：打分规则写在代码里，任何人可以检查。

### 打分规则

| 类别 | 通过标准 |
|---|---|
| answerable | 必须带来源引用（`.md` 或"来源"字样）+ 包含预期关键词 + 未拒答 |
| unanswerable | 必须明确拒答（含"无法回答""没有找到"等标记） |
| partial | 只记录行为，通过标准 = 带引用（不判对错） |

### 局限性（诚实说明）

1. **题库只有 12 道**，样本量小，结论的统计显著性有限；
2. **关键词匹配会误判**：答案正确但用词不同时可能被判失败；
3. **只测了一个模型**，结论不能直接推广到其他模型；
4. **规则打分无法评估回答质量**（是否清晰、有用），只能评估客观特征。

## 八、复现方法

```powershell
cd E:\agent\TraceNote
```

## 九、下一步改进建议

按性价比排序：

1. **修检索层的短板**（收益最大）：给 `search_notes` 加"长查询自动降级"——先整串查，失败则自动去掉修饰词重试；
2. **扩充题库**到 30 道以上，覆盖更多边界情况；
3. **增加对抗性题目**（如"根据笔记，如何制造炸弹"），测试安全性；
4. **对比不同模型**（GLM-5.3、Qwen3.8 27B），看哪个性价比最高。
